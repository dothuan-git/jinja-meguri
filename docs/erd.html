Reading the model

The calendar uses two tables. festivals defines a festival once with lore and a human-readable time_prose. festival_occurrences stores the exact dates for a given year — appended once per year after researching the shrine's official announcement. The calendar prefers the occurrence row; if none exists it falls back to festivals.start_date/end_date. Festivals with neither appear as undated fallbacks.

Lore has two layers. shrine_deities.regional_lore holds shrine-specific lore (null if the shrine uses the canonical text). deities.canonical_lore is the Kojiki-level source. Both are exposed separately — the UI layer decides how to combine them.

Deity epithets are an array. deities.titles stores all epithets (divine portfolio, human identity title) as a text[], replacing the old split domain/title columns.

Search is build-time, not DB-side. There is no shrine_search materialised view — the search blob is assembled from the in-memory store at build time and handed to Fuse.js for client-side fuzzy search.

Filters are facets, not prose. shrine_prayer_categories, shrine_ranks, region, and prefecture are all joinable — the listing page filters on rows, never on text.
